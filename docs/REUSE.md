# Reusing the port for the other games in the family (Flying Frenzy, Flounder Quest, Rooftop Ruckus)

Playbook for porting another Disney "Hot Shot" game (1999) built on the **same engine** as MuShoot. It is meant to be followed step by step by a
future session (a person, or an AI with sub-agents). Sources of the facts: `engine/docs/OTHER_GAMES_SURVEY.md` (static survey of the 4 games),
`engine/docs/ENGINE_API_COVERAGE.md` (generated by `engine/tools/engine_coverage.py`), `docs/NOTES.md` (notes of the reference game's repository), `engine/docs/README.md`.
Every statement marked **[verified]** was checked against the binaries; **[hypothesis]** was not.

This is an unofficial fan project for preservation and interoperability. The repository contains no game data and no original or decompiled code; you must own the original
games. Any reference below to the reverse-engineering workspace (`re/`, Ghidra projects, decompiled output, analysis notes) is provenance only: that material is **not part of this repository**
and nothing in the build or the tests depends on it.

Games (sibling folders in the same parent directory):

| game | folder | host exe | scene DLL | own `.rrs` archives |
|---|---|---|---|---|
| MuShoot (done) | `MUSHOOT` | `Shoot.exe` | `Shoot.dll` | `mus.rrs`, `musfx.rrs`, `muslin.rrs` |
| Flying Frenzy | `Flying` | `Flying.exe` | `Frenzy.dll` | `peg.rrs`, `pegfx.rrs`, `peglin.rrs` |
| Flounder Quest | `Flounder` | `Quest.exe` | `quest.dll` | `seb.rrs`, `sebfx.rrs`, `seblin.rrs` |
| Rooftop Ruckus | `Ruckus` | `Ruckus.exe` | `Ruckus.dll` | `abu.rrs`, `abufx.rrs`, `abulin.rrs` |

All of them also have `frenzy.rrs` + `frenzylz.rrs` (identical in the 4 games), `DDLogo.avi`/`DILogo.avi` (identical), `Launcher.exe`
(same code, different strings), `Uninst.dll` (identical), and a `.hlp` file.

## 1. What is shared and what is per game

### 1.1 Shared, reusable as is

| layer | where | evidence |
|---|---|---|
| `moses.dll`, `Aaron.dll` | `engine/moses`, `engine/aaron` | Identical SHA-256 in the 4 games **[verified]**, same 344 / 555 exports. Addresses, ordinals and the analysis of the two DLLs hold for all of them. The engine port is complete for MuShoot; the gaps for the other games are in `engine/docs/ENGINE_API_COVERAGE.md` (see §2). |
| platform | `engine/platform` | SDL2, `.rrs`, DIB RLE16, ADPCM/MIDI, AVI/MS Video 1, window. Independent of the game. The 4 games use `RAPT` as the magic of every `.rrs` (same first 16 bytes **[verified]**). `rrs_extract.py` already accepts `--game DIR`. |
| Arcade library (G1) | `engine/arcade` | Static code present **in every scene DLL**: in `Shoot.dll` it occupies 0x10013de0-0x1001da80 (40096 bytes). Searching for 24-byte windows of that range, ~70% are found again in `Frenzy.dll` (arcade at ~0x10014970), `quest.dll` (~0x1001a2c0), `Ruckus.dll` (~0x100174e0), against ~17% for the game code **[verified, byte comparison rather than function by function; the rest does not match because of relocated absolute addresses]**. The G1 port is therefore reusable; the definitive confirmation is a diff of the function lists after an export. |
| host exe + title screen (G2) | `engine/host` | The host exes are **the same program**: same `.text` size (79052 bytes), same imports (identical to `Shoot.exe`, `CreateScene` as the only export), same `RT_STRING` table (23 entries, equal), same entry point `0x102ea`, same strings "Title Screen", "Frenzy", `CreateScene`. Differences in `.text`: **3 bytes** (immediates); in `.rdata`/`.data`: a few strings; in `.rsrc`: icons/cursors. **[verified]** (§1.3). |
| build framework | `build.bat`, `CMakeLists.txt`, `tools` | See §4 and §5. |
| Launcher | `Launcher.exe` | same code (2,584-3,682 bytes different out of 32768: strings). Not part of the port. |

### 1.2 Per game

| what | notes |
|---|---|
| **Scene logic** (`Shoot.dll` -> `Frenzy.dll` / `quest.dll` / `Ruckus.dll`) | Everything above the Arcade range. This is the real work: a new package `game/<name>/` (model: `game/mushoot/`, README included). |
| **Data tables** | levels, sequences, `QUEUEMSG` queues, positions, sounds, `ArcadeGameDef`, and the table of Save/Restore lists (`int[26]`). They are generated by a script like the MuShoot one (`extract_shoot_tables.py`, specific to MuShoot: copy it and adapt it; nothing should be rewritten by hand). |
| **Strings** | the exe's `RT_STRING` table is identical in the 4 games (§1.3): `engine/tools/extract_host_strings.py` produces the same `Strings.inc`. The game strings (`.rrs` file names, `FKeys`, etc.) are in the scene DLL. |
| **Registry key** | `Software\Disney Interactive\<Game> HotShot\US`: `MuShoot HotShot`, `Flying Frenzy HotShot`, `Flounder Quest HotShot`, `Rooftop Ruckus HotShot` **[verified]**. In the port the registry is an `.ini` in `%APPDATA%\MuShoot\mushoot.ini` (`aaron/RegKey.cpp`: fixed name, **to be made per game** or the keys get mixed, although the full key is already part of the section name so there is no collision). |
| **Archive slot table** | MuShoot: `OpenArchive(0,"mus.rrs")`, `(1,"musfx.rrs")`, `(3,"muslin.rrs")`, 100 = `Frenzy.RRS`, 101 = `FrenzyLZ.RRS`. The other games' DLLs contain the same three strings `<x>.rrs`, `<x>fx.rrs`, `<x>lin.rrs` **[verified]**; the slot table (probably the same 0/1/3) **[hypothesis]**: read it in `OpenResources` (in MuShoot at 0x10012c58). |
| **Registered scene DLL** | `aaron::RegisterScene("Shoot.DLL","CreateScene",fn)` -> `"Frenzy.DLL"`, `"Quest.DLL"`, `"Ruckus.DLL"` (names from the exe's strings, §1.3). |
| **Executable name / `.ini`** | `mushoot.exe` -> one executable per game (§5). |

### 1.3 Measured differences between the host exes (from which to derive the parametrisation of G2)

Comparison of `Shoot.exe` with `Flying.exe`, `Quest.exe`, `Ruckus.exe`. Identical: `.text` for 79049 bytes out of 79052, imports, exports, the `RT_STRING` table, functions.

| what | MuShoot | Flying | Flounder | Ruckus |
|---|---|---|---|---|
| title string id (`LoadStringA(…, 0x5014, …)`, immediate in `.text` +0x1b83) | 0x5014 | 0x5015 | 0x5016 | 0x5013 |
| game-name string id for the registry key (immediate +0x1bdb) | 0x501a | 0x501b | 0x501c | 0x5019 |
| id (low word) of the title sprite (`0x658b00xx`, immediate +0x9497; in `FrenzyLZ.RRS`) | 0x25 | 0x20 | 0x1b | 0x16 |
| `.data`: default name / registry key / DLL / FX archive | "Disney's MuShoot" / `MuShoot HotShot\US` / `Shoot.DLL` / `MusFX.RRS` | "Disney's Flying Frenzy" / `Flying Frenzy HotShot\US` / `Frenzy.DLL` / `PegFX.RRS` | "Disney's Flounder Quest" / `Flounder Quest HotShot\US` / `Quest.DLL` / `SebFX.RRS` | "Disney's Rooftop Ruckus" / `Rooftop Ruckus HotShot\US` / `Ruckus.DLL` / `AbuFX.RRS` |

The `RT_STRING` table contains the titles of **all** the games (0x5012 "Disney 4 Giochi Folli", 0x5013 Abu, 0x5014 SparaMu, 0x5015 Frenesia volante,
0x5016 Flounder) and the registry names (0x5019..0x501c): the exe is a single "4 Giochi Folli" program configured by these 3 ids and 4 strings.
In the port `CShootApp::BuildAppInit` (`HostApp.cpp`) has 0x5014/0x501a **hard-wired**, and `TitleScene.cpp` has `Shoot.DLL`, `MusFX.RRS` and 0x658b0025 hard-wired.
**Recommended parametrisation** (to be done with the first following game): a `struct HostConfig { u32 titleStrId, regStrId; u32 titleSpriteId; const char *defaultName, *sceneDll, *fxRrs; }`
passed to `RunHost`; each game supplies one (values in the table). This way the G2 source stays single.

Note: the title shown in the port is the Italian 0x5014/0x5015/… string ("Disney SparaMu", "Disney Frenesia volante", ...), not the one in `.data`.

### 1.4 Where the differences are still unknown

The meaning of the fields after `RAPT` in the `.rrs` header is not verified in the survey (but the format is already decoded, see `engine/docs/rrs_format.md`, and works on 5 MuShoot archives). The `peg*`, `seb*`, `abu*` archives
must be tried with `--rrs-test DIR` **before** anything else (new resource types? Flounder has `CDibTile`, which in MuShoot "is not present in the archives": `DibData.h`).

## 3. The workflow used for MuShoot, in phases (with the agents that worked)

Real chronological order (28 commits in one day). For a new game phases 1-4 are much shorter because the engine has already been analysed and ported (§4).
Phases that use the reverse-engineering workspace (Ghidra projects, decompiled output, notes) rely on tooling that is kept outside this repository.

| # | phase | what | agents |
|---|---|---|---|
| 0 | **survey** | `engine/docs/OTHER_GAMES_SURVEY.md`: files, hashes, imports/exports, strings, comparison with MuShoot. Read-only, no file touched. | 1 Explore/general-purpose agent; `pefile` script in a scratch directory. |
| 1 | **Ghidra project** | import in the order moses -> Aaron -> game DLL -> exe -> Launcher, a script to find the game functions, 2nd analysis, names, ordinals. `lib_start.tsv`: boundary between user code and CRT (by hand, edges verified). Export of the decompiled output. | 1 agent (serialise: **only one Ghidra process** per project, see §3.2). |
| 2 | **notes per binary, in parallel** | one agent per binary (here: `shoot_exe`, `shoot_dll_a` and `shoot_dll_b` = two halves of the DLL, `aaron`, `moses`, `rrs_format`): notes function by function + a table of proposed names `names_<bin>.tsv`. Output in separate files, no conflicts. For a new game: only exe (differences) and scene DLL (2 agents, A = first half, B = second half). | N `general-purpose` agents, each with its own folder/file. |
| 3 | **merge of the names** | an agent/coordinator merges the `names_*.tsv` into `function_names.tsv` (resolving conflicts), applies the names and re-exports; commit "RE: notes + names" (here 726 names). | coordinator. |
| 4 | **engine headers / API** | interfaces before bodies: `moses/*.h` and `aaron/*.h` headers as the **contract**, `HeadersCompile.cpp` compiles them, `WORKPLAN.md` with header ownership and `CHANGES.md` for modifications. **Already done**: for a new game only the missing methods are added here (§2). | 1 architect (Plan/general-purpose). |
| 5 | **parallel packages in worktrees with stubs** | 4 engine packages (moses drawing, moses resources/audio, aaron app/window/scene, aaron widgets) each in a **persistent worktree** created by hand `.claude/worktrees/<pkg>` on a branch `engine-pkgN`. Each package writes only its own `.cpp` files; symbols of other packages not yet delivered are **temporary stubs** in a folder `engine/stubs/` (§3.2). Own headless tests (`--engine-test N`). No commits by the agents. | 4 `general-purpose` agents in parallel. |
| 6 | **integration** | merge of the branches, deletion of the stubs folder, link and semantics fixes found by the cross tests (`OnCommand` with `uintptr_t`, `FocusMgr::Lock`, pointer notifications...). Commit by commit. | coordinator (+ 1 agent for the fixes). |
| 7 | **game packages** | G1 arcade (library), G2 `shoot_exe` (host + title + popups), G3 `mushoot` (scene), also in parallel worktrees (G1 first, G2 and G3 on top). Data generated with scripts. Headless tests `--game-test arcade|host|mushoot`. | 3 agents. |
| 8 | **headless tests** | `--selftest`, `--rrs-test`, `--engine-test 1..4`, `--game-test …` (233 + 169 + 152 checks for the game packages). Never windows. | the package's agent + coordinator. |
| 9 | **verification with autoplay** | `--autoplay SCRIPT` (hidden window, scripted input, `shot` = PNG, `log`): see `README.md` ("`--autoplay` mode"), examples in `tools/autoplay/`. The PNGs are inspected with an image viewer. | 1 agent that writes the scripts and looks at the screenshots. |

For a new game the reduced path is: **0 survey (done) -> 1 Ghidra (2 binaries: exe, game DLL; the engine is already in the new project) -> 2 notes (exe: diff only, game DLL: 2 agents) -> 3 names -> §2 engine gaps (small) -> 7 scene package (1-2 agents) -> 8 tests -> 9 autoplay**.

### 3.1 What is worth doing in parallel for a new game

* Agent A: Ghidra project and export (then the project is **closed**: nobody opens it again while the others read the exported output).
* After the export, in parallel (no conflicts because they write different files): B = notes of the first half of the scene DLL, C = second half, D = diff of the host exe against the reference notes (`shoot_exe.md`), E = analysis of the 8 Aaron ordinals + `CDibTile` (if Flounder/Ruckus), F = extraction/decoding of the new `.rrs` (`--rrs-test`).
* Then: G = `HostConfig` and parametrisation of G2 (once only, for all games), H = scene package (after B, C).

### 3.2 Lessons learned (real traps of this project)

* **Antivirus software**: antivirus programs may flag freshly built executables (false positive) and delete them. Add an exclusion for the build folder (and the scratch folder) **before** compiling if needed; this applies to the repo of every new game too.
* **Rate limits**: sub-agents stop halfway. Do not restart them from scratch: **resume them with `SendMessage`** (same id) so they keep their context. Give small tasks and put the output in files (notes and tsv), not only in the final message.
* **Worktrees that disappear**: the worktrees created automatically by the agent system were deleted halfway through the work. Create **persistent worktrees by hand** under `.claude/worktrees/` (`git worktree add .claude/worktrees/engine-pkg1 -b engine-pkg1`; `.claude/` is in `.gitignore`), give the agent the absolute path, and do not use automatic isolation for long jobs.
* **Weak symbols (`__attribute__((weak))`) do not work on MinGW between different objects** (the PE/COFF linker does not choose the strong symbol as expected): use **temporary strong stubs** in a dedicated folder (`engine/stubs/PkgN_Stubs.cpp`) that is **deleted at integration**; the integrator removes it before the final merge. Never leave stubs in the final commit.
* **`cmd` does not search the current folder** when `NoDefaultCurrentDirectoryInExePath=1` is set: launch with a path (`.\build.bat`, from PowerShell `& .\re.bat`). With arguments containing spaces use PowerShell, not `cmd //c` from git-bash.
* **GUI-subsystem exe**: console output does not appear; capture it with `Start-Process -NoNewWindow -Wait -RedirectStandardOutput f.txt`. The port's main does `AttachConsoleOutput` for the tests.
* **Do not drive the user's real desktop**: no `build.bat run`, `--movie` or normal launch without warning (the user may be playing). Use `--autoplay`: hidden window, synthetic input, screenshots to file. Do not kill processes by name.
* **Ghidra project locking**: a project cannot be opened by two processes (`.lock` file, half-written database); with the GUI open `export`/`names` fail; never commit with Ghidra open. For experiments use a separate project and another export folder; never touch the main project while experimenting.
* **Safe parallelism**: each agent has *its* files (ownership rule in `WORKPLAN.md`); whoever modifies someone else's header writes it in `CHANGES.md` under REQUESTS. The integrator is the only one who commits.
* Interactions with other active sessions: files such as `main.cpp`, `Window.*`, `CMakeLists.txt`, `README.md`, `CLAUDE.md` are hot spots; check `git status` before touching them.
* The user-code / library boundary in `lib_start.tsv` is a heuristic: re-check it for every new game DLL (the end of the user code is where the import stubs begin, then the CRT).

## 4. Bootstrap with `engine/tools/new-game.ps1` and `re/game.cfg`

> **Two-repository layout (19/10/2026, adopted).** The engine is the `rapture-engine` repo, a git submodule `engine/` of one repo per game (a private `<game>-rapture-port` repo): this is option A of §5, with one repo per game.
> Clone: `git clone --recurse-submodules`; `build.bat` runs `git submodule update --init` by itself if `engine/` is empty. The reverse-engineering workspace (Ghidra projects, analysis notes and decompiled output)
> is maintained outside this repository; each game keeps its own only for what is specific to it (scene DLL, `Launcher.exe`, optionally the host exe if a comparison is wanted).

### 4.1 `re/game.cfg` and `re.bat` (optional, reverse-engineering workspace only)

The generic `re.bat` and the Ghidra scripts contain no binary names: everything comes from the configuration file of the workspace (`KEY=VALUE` keys, `#` = comment).
A game's `re.bat` is a 3-line wrapper (`RE_ROOT`, `RE_GAME_CFG`, `call engine-re\re.bat %*`). None of this is needed to build or test the port.

| key | meaning | MuShoot (`re/game.cfg`) | engine |
|---|---|---|---|
| `PROJ_NAME` | name of the Ghidra project (`re\projects\<PROJ_NAME>.gpr`) | `Mushoot` | `Rapture` |
| `GAMEDIR` | folder of the original binaries (relative to the repo root or absolute) | `..` | `..\..` |
| `FALLBACK_DIRS` | other folders where a missing binary is searched | - | - |
| `MAIN_EXE` | a binary that must exist in `GAMEDIR` | `Shoot.dll` | `Shoot.exe` |
| `BINARIES` | all the binaries of the project | `Shoot.dll Launcher.exe` | `moses.dll Aaron.dll Shoot.exe` |
| `IMPORT_ORDER` | import order of `rebuild` | `Shoot.dll Launcher.exe` | `moses.dll Aaron.dll Shoot.exe` |
| `RESOLVE` | binaries whose Aaron (ordinal) / moses (decorated name) imports are renamed | `Shoot.dll` | `Aaron.dll Shoot.exe` |
| `NAMES` | name files, applied in order | engine + game | `re\notes\function_names.tsv` |
| `EXPORTS_FROM` | folders with `<DLL>\exports.txt` for DLLs outside the project | `engine-re\re\out\current` | - |

`re.bat config` prints the resolved configuration and the binaries found (without Ghidra). A game repo with its own binaries adds the lines for their code/CRT boundary to `re/lib_start.tsv`.
A game's Ghidra project contains **only its own binaries**: the moses/Aaron imports are named from the engine's `exports.txt` tables, without importing the DLLs.
Verified on 19/10/2026 on MuShoot: the decompiled output of `Shoot.dll` and `Launcher.exe` from the new project is identical (`decomp.c`, `functions.tsv`, `exports.txt`) to the one
obtained with the DLLs in the project; only the order of the lists in `info.txt` and two header/column lines in `imports.txt` change.

Other path-independent scripts: `engine/tools/rrs_extract.py [--game DIR]`, `engine/tools/extract_host_strings.py HOST.exe OUT.inc [LANGID]` (valid for every host exe),
and the game repository's `extract_shoot_tables.py [GAME_DLL]` (variable `GAME_DLL`; specific to MuShoot: it is a **model** for the extractors of the other games).

### 4.2 `engine/tools/new-game.ps1`

```
.\engine\tools\new-game.ps1 -GameDir "<games-dir>\Flying" -Name flying -Title "Flying Frenzy" [-EngineUrl <url>] [-CopyEngine] [-NoCommit] [-Force] [-DryRun]
```

To be run **only by the user** (or with their explicit consent) on the real game folder; it writes **only** `<GameDir>\src` (nonexistent or empty, unless `-Force`), does not touch the original files, and starts nothing.
`-DryRun` only prints what it would do. Tried on 19/10/2026 on a scratch folder with the Flying files (initial commit, `.gitmodules`, submodule pointer, working `re.bat config`). What it produces:

1. checks that `moses.dll`/`Aaron.dll` are identical (SHA-256) to the MuShoot ones; detects the host exe and scene DLL;
2. `CMakeLists.txt` (`add_subdirectory(engine)` + `game/**.cpp`), `build.bat`, `re.bat` (wrapper), `.gitignore`, `.gitattributes`, `game/main.cpp`, `game/HostConfig<Game>.{h,cpp}` (to be filled in), `game/Strings.inc` (with
   `extract_host_strings.py` if python + pefile are available);
3. the engine: `git submodule add <url> engine` (url = `origin` of the engine that contains the script, or `-EngineUrl`); with `-CopyEngine` a copy (not recommended: it diverges);
4. a filled-in `re/game.cfg` (the game's binaries; `NAMES`/`EXPORTS_FROM` point to the engine's workspace), `re/lib_start.tsv` (TODO lines), `re/notes/` with skeletons for the exe and the scene DLL, `binaries.md`, an empty `function_names.tsv`,
   and the notes of the reference game in `re/notes/reference-game/`; `CLAUDE.md` (model) and `docs/NOTES.md` (skeleton with the checklist);
5. `git init` + first commit (skipped with `-NoCommit`).

## 5. Recommended layout for several games

### 5.1 Options

| | A. one repo per game, engine as a shared submodule, one executable per game | B. one repo per game, engine copied (`new-game.ps1`) |
|---|---|---|
| structure | `engine/platform`, `source/engine`, `engine/arcade`, `game/host` (parametric G2) as static libraries; `game/mushoot`, `…/flying`, `…/flounder`, `…/ruckus` each with its own `main` and CMake target | every game has its own repo with a copy of platform/engine/arcade/host |
| engine fixes | made once, valid for all games, the headless tests of the other game verify them immediately (regressions seen) | have to be carried over by hand to N repos; divergence is inevitable |
| RE data | kept outside this repository (private workspace), per game, with a shared part for the engine (moses/Aaron are identical) | duplicated; the engine notes get copied |
| repo contents | no game data, no original or decompiled code in the public repositories | separate repos (but each contains the engine) |
| build | a single CMake; `build.bat <game>`; timing: the engine library is compiled once | simple and isolated |
| risk | an engine change for one game can break another (mitigated by the tests) | silent divergence |
| work to get started | refactoring of CMake and `main.cpp` (one-off, §5.3) | `engine/tools/new-game.ps1` and nothing else |

### 5.2 Recommendation

**Option A (shared engine)**, because engine, platform and Arcade are by definition identical (bit-for-bit binaries) and the engine's headless tests
(140+273+101 checks) become the safety net of all the games; the real differences are very few (§2). Option B (`new-game.ps1`) remains useful to
**prototype the analysis** of a game in a separate folder without touching the MuShoot repo (that is why it was written this way) and then carry the engine changes back
into repo A with `git`/`diff` (`ENGINE_VERSION.txt` says which commit it started from).
Suggested order: (1) do the analysis of the first game (Flying, the closest: no new ordinal, 2 moses symbols already present) with B; (2) when the engine changes are few
